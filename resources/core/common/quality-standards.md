# 质量标准

> 框架规则版本 10.5 | 2026-07-08 | 维护者：Thinker Agent
> Source Status: canonical
> Scope: 质量红线、生产级标准、自行验证、错误诊断

所有Agent引用的质量标准，包括质量优先级、安全红线、Clean State原则和大型开发质量保证原则。约束由编排纪律与提示词执行，不依赖门禁机制。不可妥协的底线项（按 task_tier 分档时不得放松）见 resources/core/common/immutable-baseline.md。

---

## 质量优先级

| 级别 | 维度 | 说明 |
|------|------|------|
| 1 | 安全性 | 数据安全、系统稳定、不崩溃 |
| 2 | 正确性 | 功能符合需求、逻辑正确 |
| 3 | 可维护性 | 代码清晰、易于修改 |
| 4 | 性能 | 运行效率、资源使用 |
| 5 | 美观性 | 界面美观、代码整洁 |

## 安全红线

| 约束 | 执行方式 |
|------|---------|
| 禁止未测试就提交 | 语义判断 - 交付前必须完成与改动/风险相称的验证（L1 冒烟不可省） |
| 禁止测试失败仍提交 | 语义判断 - 测试失败必须修复后方可提交 |
| 禁止无验证报告交付 | 语义判断 - 已交付文件需包含验证信息 |
| 禁止跳过检查点 | 质量思维 - 渐进式开发中必须验证每步 |
| 禁止猜测主上意图 | 认知约束 - 不确定时必须询问而非假设 |
| 禁止使用emoji | 提示词约束 - 代码和文档中禁止emoji字符 |
| 禁止质量降级 | 语义判断 - 每次修改必须维持或提升质量水平 |
| 禁止模块未备份就集成 | Git流程 - 成功状态必须commit保存 |
| 禁止依赖 Shell 变量展开（$VAR_NAME） | 提示词约束 - 使用绝对路径或Python脚本，禁止$VAR_NAME语法 |
| 禁止请求主上手动验证（Agent必须自行完成所有验证） | 提示词约束 - Agent必须自行完成所有验证，禁止写入"请手动验证"等短语 |
| 禁止硬编码假数据/mock数据/占位符数据 | 提示词约束 - 禁止mock_data、test@test.com等占位符数据（测试文件除外） |
| 禁止简化实现/降级实现/demo级实现 | 语义判断 - 所有实现必须达到生产级标准 |
| 禁止将Web交互测试降级为API测试 | 测试策略约束 - Web功能必须通过浏览器交互验证 |
| 禁止将错误归咎于服务器未重启/缓存未清理而不排查代码 | 诊断约束 - 必须基于代码分析而非环境推测 |

## Clean State 原则

每次会话结束时，代码库必须可运行。

| 场景 | 操作 |
|------|------|
| 功能成功 | `git commit -m 'feat: xxx'`（保存稳定状态） |
| 功能失败 | `git reset --hard HEAD`（回退到上一轮） |
| 改乱了 | `git reset --hard HEAD`（瞬间恢复干净） |

## 生产级标准

所有实现必须达到生产级上线标准，而非Demo/MVP/原型标准。

**必须满足**：

- 完整的错误处理和边界情况覆盖
- 真实的数据流和业务逻辑
- 完整的用户交互流程
- 生产级的UI/UX质量
- 完整的状态管理（加载态、空态、错误态、成功态）
- 符合项目既有代码质量水平的实现标准

**反模式（禁止）**：

- TODO/FIXME/HACK占位符 - 禁止在生产代码中使用
- 硬编码返回值或假数据充当业务逻辑 - 禁止mock_data等占位符数据
- 用 console.log/print 替代正式的错误处理
- 省略表单验证、权限检查、数据校验
- 用简单alert/confirm替代正式UI反馈组件
- 跳过复杂功能只实现骨架代码
- 用注释描述"此处应实现xxx"而未实际实现 - 禁止骨架代码

## 自我验证规范

Agent必须自行完成所有验证，绝不能要求主上手动验证。

验证是Agent的职责。禁止短语由提示词约束：请手动验证、请自行验证、请检查、需要你验证等。

验证范围与改动/风险相称：L1 冒烟（构建通过、启动正常、关键路径验证）任何代码变更不可省；针对性测试必须映射验收条件或真实失败风险；全量回归仅高风险路径、发布前或主上明确要求时执行。

**验证动作（按改动/风险选择相称范围，L1 冒烟不可省）**：

- 代码编译/构建验证：运行构建命令确认无错误
- 单元测试验证：运行测试套件确认通过
- 功能验证：通过脚本或工具验证功能正确
- 前端验证：使用agent-browser进行浏览器交互验证
- 集成验证：启动服务并验证端到端流程

## 错误诊断规范

错误诊断必须基于代码分析和证据，禁止归咎于环境因素。

**正确的诊断流程**：

1. 首先阅读完整的错误信息和堆栈跟踪
2. 在代码中定位错误发生的具体位置
3. 分析代码逻辑找到根本原因
4. 如果确实怀疑环境因素，必须先用工具验证（检查进程、端口、日志）
5. 修复代码后运行测试验证修复效果

## Web交互测试标准

当任务要求Web交互测试时，必须执行真实的Web交互测试。

Web交互测试不可降级为API测试——它们验证的是不同层面的正确性。

**规则**：

- 前端功能必须通过浏览器交互验证（agent-browser）
- 遇到选择器问题时，应使用侦察模式发现正确选择器，而非放弃
- 遇到页面加载问题时，应调试等待策略，而非降级为API测试
- API测试和Web交互测试是互补的，不是替代关系
- 测试报告必须包含浏览器截图证据
